# 图片顶栏「裁剪」迁移计划书（v1 · 待你确认）

> 目标：把 ComfyUI 里 `Goohai 加载图库` 节点的裁切手感搬到画布图片顶栏的「裁剪」上——**在原图上预览裁切、向下游传裁切结果、结果可再次编辑**，整体形态与已经迁移完成的「遮罩」「批注」一致（独立全屏编辑器 + 就地写回原图片条目）。
> 本文只描述方案，不改代码。读完请确认第四节的理解与第五节的拍板项。

## 一、我理解的需求

| 你的原话 | 我的理解 |
| --- | --- |
| 「了解一下这个节点的裁切功能」 | 只研究 `Goohai 加载图库` 里的 `crop` 那部分（隐藏 JSON 控件 + 原图上的选框 + 输出裁切结果），图库分类、翻页、收藏、随机、上传这些都不迁。 |
| 「迁移顶替当前画布的图片顶部菜单栏的‘裁切功能’」 | 是**替换**，不是新增第二个按钮。顶栏 `裁剪`（`static/smart-canvas.html:142`）以后打开新编辑器；旧弹窗里的 crop 模式下线。 |
| 「裁切效果在原图预览」 | 编辑器里底图永远是**原图（有批注时是批注后的整图）**，选框直接压在上面、框外压暗，所见即所得；不会在编辑器里把画面换成一截裁好的小图。 |
| 「向下传递的时候传递裁切结果图」 | 下游拿到的是裁切后的图：生成参考图、ComfyUI 的 LoadImage、工作流输入、复制/导出、下载、推送到 Photoshop、存素材库，都应该是裁切结果。 |
| 「裁切图可以再次编辑」 | **非破坏**：原图永远留着，只额外记一个归一化选框（0–1）。再次点「裁剪」= 打开原图 + 上次那个框，可以改、可以清空还原。不是现在这种"裁完就生成一个新节点、原节点和新节点各一份"。 |
| 「类似遮罩和批注功能」 | 同一套外壳与契约：`window.CropEditor.open({...}) → Promise<boolean>`，`onSave(result)` 被 `await`，保存后**就地写回同一张图片条目**，不新建节点；样式复用 `mask-editor.css` 的 `.me-` 设计令牌。 |

一句话总结：**把「裁剪」从"一次性生成新节点"改成"和遮罩/批注一样的非破坏编辑层"——原图上看效果，下游用裁切结果，随时能进编辑器再调。**

## 二、Goohai 那套裁切到底强在哪

| 能力 | Goohai 的实现 | 迁到画布后的对应物 |
| --- | --- | --- |
| 裁切参数怎么存 | `crop` 是**隐藏的字符串控件**，里面是 JSON：`{"type": 当前分类, "image": 当前图 ID, "ratio": "自由/1:1/...", "rect": [x,y,w,h]}`，rect 全部按原图归一化到 0–1 | `image.crop`（见 4.1）。归一化是关键：换预览尺寸、换缩放都不影响结果。 |
| 什么时候失效 | `crop_bounds()` 发现 json 解析失败、`type`/`image` 与当前图不一致、rect 不是 4 个有限数、w/h ≤ 0 → 直接返回 None，不裁 | 记 `source` 签名（原图 url + 批注 url + 原始尺寸），底图一变就重算，不会拿旧框去裁新图。 |
| 输出怎么生效 | `execute()` 里对张量 `output[:, top:bottom, left:right, :]`；像素边界用 `floor(x*W+.5)` 再 `clip`，不会越界 | 浏览器 canvas 按同一套取整规则裁出 PNG，再走现有 `/api/ai/upload`。 |
| 改框要让缓存失效 | `fingerprint_inputs` 返回 `(文件摘要, prompt, crop)`，`IS_CHANGED` 同源 | 每次确认都重新上传/写签名，`crop.result` 里的 url 变了，任何下游缓存自然失效。 |
| 预览怎么显示 | 非编辑态：用 canvas 把原图按 rect 裁成 dataURL 当预览；编辑态：换回原图。**同一个预览区两种状态** | 节点上显示 `crop.result`（裁切结果）+「已裁切」角标；编辑器里显示原图。 |
| 编辑手感 | 竖排在图左的比例栏（自由/1:1/2:3/3:2/3:4/4:3/9:16/16:9/21:9/1:2/2:1）+「清除」；框外 `clip-path: polygon(evenodd, …)` 压暗；三分线 + 中心十字（按取样亮度自动黑/白）；8 个手柄；拖空白重画、拖框内平移、手柄缩放；Shift 锁 1:1、Alt 中心对称；方向键 1px / Shift+方向键 10px；双击或 Enter 确认、Esc 取消 | 全部照搬（键盘/手柄/比例栏），滚轮与空格平移改成画布已有的手感。 |
| 提交时机 | `promptQueueing` 事件里 `confirmForQueue()`：点"运行"前把正在编辑的裁切一起提交 | 画布不需要这一层：点「应用」才落盘，未点应用就关掉 = 丢弃。 |

顺带一个对照：ComfyUI 原生 `ImageCropV2`（`IO.BoundingBox.Input("crop_region", component="ImageCrop")` + `PreviewImage`）是"独立裁切节点 + BoundingBox 控件"；Goohai 是"节点内嵌裁切 + 隐藏字符串控件"。**我们要的是后者**——裁切不出现新节点，参数挂在图片条目上。

## 三、画布现状

| 位置 | 现在是什么样 |
| --- | --- |
| 顶栏按钮 | `static/smart-canvas.html:142` `data-image-toolbar-action="crop"`，文案「裁剪」，图标 `crop`。和它同一排的 `mask`/`brush` 已经改成打开独立编辑器。 |
| 点击后 | `smart-canvas.js:11768` 把 crop 归到"图片编辑弹窗"那一组：`openImageEditor(node.id,index)` + `setImageEditMode('crop')`。弹窗里还有 outpaint / resize / grid 三个模式共用这套壳。 |
| 应用后 | `applyImageCrop()`（`:19670`）读 `#cropImage` 的 `naturalWidth/clientWidth` 换算像素 → canvas 裁 → `uploadCroppedBlob` → `replaceEditedImage()` → **在原节点右侧新建一个单图节点**，并 `delete image.annotation / annotationPaint`。原节点保留原图，但裁切参数不落盘，**无法再次编辑这个框**。 |
| 可复用的地基 | `imageForDisplay(img)`（`:9865`）已经是"显示用条目"的唯一收口：有 `annotation` 就返回批注图。节点预览（`:10800`）、缩略图、`imagesForNode()`（`:21378`）、`promptRequestRefs()` 全部经过它或它的产物。 |
| 已经验证过的迁移范式 | `mask-editor.js` / `annotation-editor.js`：原生 ES2019、无构建、`window.XEditor.open()` 单出口、`class XSession`、`await this.onSave(result)`、`resolve(!!saved)`、就地写回 `image.mask*` / `image.annotation*`、静态契约测试 `tests/test_mask_editor.py` / `test_annotation_editor.py`。 |

三条现状事实：

1. 现在的裁剪是**破坏性 + 派生新节点**，与"可再次编辑"直接冲突，必须换实现，不能只换 UI。
2. 图片条目的字段是自由结构，服务端 `validate_canvas_node_fields()`（`main.py:6600`）明确不维护图片字段白名单，**新增 `image.crop` 不需要改 main.py**，也不需要迁移旧数据（没有 crop 就是没裁过）。
3. `images` 是单个节点字段，改 `images[i].crop` 会整数组随 `node_fields` 操作同步——和遮罩/批注一样的并发语义，不引入新的同步机制。

## 四、迁移方案

### 4.1 数据模型（放在图片条目上）

```js
image.crop = {
  rect: { x, y, w, h },      // 归一化 0–1，相对"原图/批注整图"
  ratio: 'free' | 'source' | '1:1' | '4:3' | ...,
  width: 1024, height: 1024, // 裁切结果像素尺寸（角标、布局、排查用）
  source: {                  // 生成签名：底图变了就重算，不复用旧结果
    url, annotationUrl, natural_w, natural_h
  },
  result: {                  // 实际向下游传递的那张图（资产 URL）
    url, name, kind: 'image', natural_w, natural_h
  }
}
```

- 老数据：字段不存在 → 全链路行为不变。
- `delete image.crop` = 还原原图（编辑器里的「清除裁切」）。
- `crop.result` 是真实上传的 PNG（原图像素裁出，不缩到 1536），所以下游、导出、PS、素材库都当普通图片处理，ComfyUI 也不需要特判。

### 4.2 编辑器形态

- 新文件 `static/js/crop-editor.js` + `static/css/crop-editor.css`，外壳、工具条、面板、缩放/平移、Toast 全部复用 `mask-editor.css` 的 `.me-` 令牌，只补裁切独有的选框/手柄/遮罩/比例栏样式。
- API：`window.CropEditor.open({ imageUrl, rect, ratio, labels, onSave }) → Promise<boolean>`；`result = { rect, ratio, width, height, blob }`。
- 九个比例预设：`自由 / 原图 / 1:1 / 4:3 / 3:4 / 16:9 / 9:16 / 3:2 / 2:3 / 21:9`（"原图"= 保持底图比例；相比 Goohai 少了 1:2、2:1，待你定，见 5.5）。
- 顶部工具条：`清除裁切`（清掉 rect 回到整图，点应用才落盘）、`重置`（回到刚打开时的框）、`取消 / 应用`。
- 画布内：框外压暗 + 三分线 + 中心十字 + 8 手柄；拖空白重画、拖框内平移、手柄缩放；Shift 锁当前比例、Alt 中心对称；方向键微调；滚轮缩放、空格/中键临时平移、双击或 Enter 应用、Esc 取消。
- "在原图预览"：底图 = `imageBaseForDisplay(img)`，也就是**裁切之前**的图（有批注就是批注图）。再次打开时按 `image.crop.rect` 还原选框。

### 4.3 显示与节点

- `imageForDisplay` 拆两层（关键改动，两行代码的差别但影响全局）：
  - `imageBaseForDisplay(img)`：现有逻辑（annotation → 本地代理 url）。
  - `imageForDisplay(img)`：先 `base`，若有 `crop.result` 则返回 `{...base, url: crop.result.url, natural_w: crop.width, natural_h: crop.height}`。
- 于是节点大图、缩略图、分辨率角标、`imagesForNode()` 全部自动变裁切图。
- 角标：沿用 `.mask-overlay-label` 样式，在裁切图上显示 `已裁切 · 1024×1024`（i18n）。
- 节点尺寸：**默认不动 `node.w/h`**，裁切后图片按 `object-fit: contain` 落在原节点框里，避免一次裁切把用户排好的画布挤乱；分辨率角标显示裁切后的真实尺寸。若你想要"节点跟着裁切比例走"，见 5.4。

### 4.4 再次编辑

点顶栏「裁剪」→ `openCropEditorForImage(node, index)`：

1. 取 `imageBaseForDisplay(item)` 当底图；
2. 传 `rect: item.crop?.rect`、`ratio: item.crop?.ratio`；
3. 编辑器按 rect 还原选框 → 用户调整 → 应用 → 重新裁 → 上传 → 覆盖 `image.crop`。

如果选框和上次完全一致（且 `source` 签名没变），直接复用旧 `result`，不重复上传。

### 4.5 向下传递（重点核查）

主要靠 `imageForDisplay` 收口，但有四处要显式改：

| 位置 | 改动 |
| --- | --- |
| `promptRequestRefs()`（`:22113`） | URL 优先级改为 `crop.result > annotation > maskColor > url`；`crop` 存在时仍按原规则决定是否带 `mask`（遮罩本来就是画在裁切图上的，尺寸天然一致）。 |
| `openMaskEditorForImage()`（`:19918`） / `openAnnotationEditorForImage()`（`:20050`） | 遮罩编辑器的底图改成 `imageForDisplay(item)`（裁切后的图），保证遮罩坐标与下游那张图对齐。批注编辑器仍用整图（见 4.6 的顺序）。 |
| `comfyNameForMaskedRef()` / `assignComfyWorkflowMediaValues()` | 不用改：它们拿到的 ref.url 已经是裁切结果。 |
| 其余直读 `img.url` 的地方 | 交付前 grep 一遍并逐个确认：`downloadPreviewFile`、Photoshop 推送、复制/粘贴、工作流 ZIP 导出、素材库收藏、历史记录缩略图。凡是没有经过 `imageForDisplay` 的，都要补上。 |

### 4.6 与批注 / 遮罩 / 颜色叠加的顺序

提议固定为：

```
原图 → 批注（始终在整图上，裁切时把批注一起裁进去）
     → 裁切（rect 相对整图）
     → 遮罩 / 颜色叠加（画在裁切后的图上）
     → 向下传递
```

理由：

- 批注是"在整图上做标记"，先批注后裁切的常见流程（先标重点再裁一块）能保留下批注；若反过来，批注会被永久锁在裁切图坐标系里，之后想扩大裁切范围就取不回批注。
- 遮罩是"告诉模型改哪里"，必须和送出去的那张图逐像素对齐，所以只能在裁切之后画。
- 改裁切时：批注自动保留（一起裁）；遮罩需要处理——见 5.2 的三个选项（推荐按 rect 重映射，其次清空并提示）。

### 4.7 持久化与同步

- `image.crop` 随 `images` 数组进 `node_fields` 操作，`clear_fields` 删除走现有机制（`delete image.crop` → diff 出 `clear_fields` 里没有的键？注意：`images` 是整数组字段，删键体现为数组内容不同，仍走 `node_fields` 值覆盖，不需要新 op）。
- 撤销：应用前 `pushUndo()`（和遮罩/批注一致）。
- 双标签页：同一张图同时改裁切/遮罩仍会后写覆盖，与现有 mask/annotation 风险同级，本次不新增机制。
- 不做 `main.py` 改动；`tests` 里已有的服务端契约测试不受影响。

### 4.8 旧弹窗裁剪怎么退场

- `runImageToolbarAction()` 里把 `crop` 从"弹窗三兄弟"移出，改走 `openCropEditorForImage()`。
- `#imageCropTools`、`#cropBox`、`.crop-handle`、`cropState/cropDrag/cropAspectPreset/cropAspectRatio`、`resetCropBox()`、`applyImageCrop()` 从图片编辑弹窗的路径里摘掉（`outpaint` / `resize` / `grid` 保持原样，仍用弹窗）。
- 旧函数按 5.6 拍板处理：选 A 就与接线同一次提交删干净；选 B 才保留，且**清理是一个显式的独立提交，条件是阶段 4 实测通过**——没有任何机制会自动删除它，若 14 天内没做清理，要在本文顶部标一条待办，避免它变成死代码。

## 五、需要你拍板的事

1. **「另存为新节点」还要不要保留？**
   现在裁剪会派生一个新节点；新方案是就地非破坏（原图还在 `image.crop` 里，随时「清除裁切」还原）。
   - A（推荐）只做就地，不新建节点——画布更干净，符合"再次编辑"。
   - B 就地为主，另外在右键菜单留一个「裁切结果另存为新节点」，给需要把裁切图当独立素材用的场景。

2. **改裁切时，已有的遮罩怎么办？**
   - A（推荐）按新旧 rect 重映射：把旧遮罩图按坐标映射画到新视野里，超出部分裁掉，用户不用重画。
   - B 直接清空并提示"裁切范围变化，遮罩已重置"（实现最简单、最不会错位）。
   - C 保留原遮罩不动——会与裁切图错位，不建议。

3. **批注和裁切的先后顺序确认。**
   - A（推荐）批注 → 裁切：批注永远在整图上，裁切保留批注；**裁切后想再批注时，批注编辑器仍打开整图**，批注图整体裁切后生效。
   - B 裁切 → 批注：批注只能画在裁切图内，改裁切会丢批注。若你实际在"裁完再标"的场景更多，也可以选 B，但要接受这个代价。

4. **节点尺寸要不要跟裁切比例走？**
   - A（推荐）不动 `node.w/h`，只换图（contain），布局稳定。
   - B 裁切后按新比例把节点缩放到合适大小（会动别人的画布排布）。

5. **比例预设集合。**
   - A（推荐）自由 / 原图 / 1:1 / 4:3 / 3:4 / 16:9 / 9:16 / 3:2 / 2:3 / 21:9（画布现有 9 个 + 21:9 + 原图）。
   - B 与 Goohai 完全一致：再加 1:2、2:1，共 13 个。

6. **旧裁剪代码怎么退场？**
   - A（推荐）**本次提交就删干净**：入口切走、`applyImageCrop()` / `resetCropBox()` / `#cropBox` 等一并删除。测试与实测都会覆盖，真出问题用 `git revert` 回滚这一个提交即可，不必在代码里留旧函数当保险。
   - B 本次只切入口、旧函数保留，等阶段 4 实测通过后再单独提一个"删除旧裁剪路径"的提交（回滚粒度更细，但需要有人记得做，否则就是死代码）。
   - C 额外留 `?legacyCrop=1` 开关——不建议，多一条没人维护的分支。

## 七、风险与坑

1. **坐标系混用**：旧 `applyImageCrop()` 用 `naturalWidth / clientWidth` 现算比例，一旦编辑器有缩放/平移（新编辑器一定有）就会错。新实现统一维护"原图像素 ↔ 编辑区 CSS 像素"两个矩阵，所有手柄与鼠标事件只走这一套换算，并在应用时按原图坐标 `floor(x*W+.5)` 取整、夹紧（照 Goohai 的 `crop_bounds`）。
2. **超大图**：裁切不缩放，直接按原图像素 `drawImage`。Chrome canvas 单边上限约 16384，4 亿像素会 OOM；打开时检测，超限就提示"图片过大，暂不支持裁切"而不是崩掉。
3. **下游遗漏**：`imageForDisplay` 收口能覆盖绝大多数，但历史记录、素材库、PS 推送、ZIP 导出可能直读 `img.url`——这是最容易漏的一块，按 4.5 的清单逐个验证。
4. **遮罩错位**：改裁切后若选 5.2-B（清空），必须先弹确认；选 A（重映射）要保证映射只做一次，避免反复裁切后累积模糊（映射仍用 `imageSmoothingEnabled` 默认，缩小时会轻微软化，可接受；或在提示里说明）。
5. **撤销后孤儿文件**：撤销不会删上传的裁切图，和遮罩/批注一致，不额外做回收。
6. **多图节点**：裁切作用于 `selectedImage` 指向的那一张，和遮罩/批注一致；切换主图不会互相影响。
7. **视频 / 动图**：顶栏裁切只对图片（`mediaKindForItem === 'image'`），视频保持现状（继续走「截取片段」「帧工具」）。
