# 部门独立 API 配置组：设计与迁移方案

> 文档状态：实施中，作为改造的统一实施依据
> 当前阶段：M1-M4 主体已实现；M5 异步任务持久化、任务所有者和扩展身份链已完成代码与自动化验收，待真实客户端手工冒烟
> 最后更新：2026-08-01

## 1. 背景与目标

当前系统由多个部门共同使用同一套 API 平台与充值账户。随着使用量增长，需要做到：

- 每个部门使用独立申请、独立充值的上游 API 账户；
- 所有 API 账户仍由系统管理员统一维护；
- 保留一个服务端和一个访问地址；
- 普通用户只能使用自己被分配的 API 配置组；
- 即使用户修改前端请求，也不能调用其他部门的凭据；
- 图片、视频、LLM、异步任务和扩展入口均遵守同一隔离规则；
- 用量可以按稳定的经费归属统计，并与上游账单对账；
- 改造期间保持旧用户、旧画布、旧任务和现有共用配置可用。

本次改造采用“单实例、服务端强制配置组隔离”，不建设四套重复服务。

## 2. 范围与非目标

### 2.1 本次范围

- API 配置组及其平台连接的数据结构；
- 用户与 API 配置组的管理员绑定；
- API 设置页中的配置组管理与切换；
- 服务端按登录用户解析有效平台与凭据；
- 所有付费或重计算入口的配置组隔离；
- 异步任务提交、执行、轮询和恢复的配置组固定；
- Chrome、Photoshop 等扩展入口的同等隔离；
- 配置组级审计、配额、告警和对账字段；
- 旧全局平台配置向兼容配置组的平滑迁移；
- 灰度切换、回滚和旧共用账户退役。

### 2.2 非目标

- 不拆分为四套服务端；
- 不引入数据库或迁移框架；
- 不重写现有前端技术栈；
- 不在本次改造中顺带重做画布、素材库或生成页面；
- 不默认替换现有上游平台；
- 不通过真实付费批量生成承担主要测试；
- 不把部门名称直接当作权限或密钥索引。

## 3. 术语与实体

### 3.1 部门

组织信息，例如 UI 组、原画组。部门名称用于展示和人员管理，不作为安全边界。

### 3.2 API 配置组

稳定的经费与凭据作用域，建议内部字段名为 `api_profile_id`。一个配置组包含若干平台连接、默认平台、启停状态和配额策略。

当前可以让一个部门对应一个配置组，但数据结构不写死一一对应关系，以支持：

- 多个部门临时共用一个经费账户；
- 同一部门按项目拆分经费；
- 公司统一承担的共享服务；
- 部门改名但历史账目归属不变。

### 3.3 平台定义

平台的协议、默认地址、模型能力和系统模板等可复用信息，例如 OpenAI 兼容、RunningHub、火山引擎、ModelScope。

### 3.4 平台连接

配置组内对某个平台的实际启用实例，包括：

- 平台 ID；
- 是否启用；
- 是否为默认平台；
- Base URL；
- 可见模型；
- 必要的协议或端点覆盖；
- 凭据引用；
- 计费性质。

同一个平台 ID 可以同时存在于多个配置组中，但解析键必须是 `(api_profile_id, provider_id)`。

### 3.5 计费性质

建议至少支持：

- `department`：由当前配置组承担费用；
- `shared`：公司或公共经费承担；
- `local`：本地 ComfyUI、CLI 等非外部充值资源；
- `disabled`：该配置组不可使用。

共享账户不得作为部门账户失败后的静默兜底。

## 4. 不可违反的系统原则

以下规则是后续代码审查和验收的最高优先级约束：

1. 部门文字不是权限依据，服务端只认稳定的 `api_profile_id`。
2. 普通用户不能决定、覆盖或伪造自己的 API 配置组。
3. 每次请求必须根据服务端认证身份解析配置组。
4. 不得按请求切换全局环境变量、全局“当前部门”或全局平台列表。
5. 用户明确指定的平台在本组不存在时必须报错，不能跨组回退。
6. 未明确指定平台时，只能回退到当前配置组自己的默认平台。
7. 异步任务提交时必须固定 `user_id`、`api_profile_id` 和平台 ID。
8. 任务执行与轮询不得重新相信客户端提供的配置组。
9. API Key、AK、SK、Cookie 和上游 Token 不得进入浏览器响应、任务记录、审计日志或错误日志。
10. 所有付费入口必须通过同一个服务端作用域解析层。
11. 配置组停用后不得提交新任务；既有任务的处理策略必须明确。
12. 历史审计保存提交时的配置组快照，不能因部门改名或用户调组而变化。
13. 管理员管理所有配置组，但普通用户只能读取自己的有效平台能力。
14. Chrome、Photoshop 和网页端遵守相同的服务端隔离规则。
15. RunningHub 钱包 Key、火山 AK/SK 等特殊凭据必须与普通 API Key 一样按配置组隔离。

## 5. 目标数据结构

以下结构为概念方案，正式字段以实施阶段确认的 Pydantic 模型和兼容要求为准。

### 5.1 用户

```json
{
  "id": "user-id",
  "username": "zhangsan",
  "name": "张三",
  "department": "UI组",
  "api_profile_id": "ui-budget",
  "role": "user",
  "enabled": true,
  "quota": {}
}
```

规则：

- `department` 继续作为组织信息；
- `api_profile_id` 由管理员分配；
- 新注册用户默认进入“待分配”状态，不能仅凭自填部门获得付费权限；
- 管理员变更用户配置组后，新请求立即使用新组；
- 已提交异步任务继续使用提交时的配置组。

### 5.2 API 配置组

建议新增非敏感配置文件，例如 `data/api_profiles.json`：

```json
{
  "version": 1,
  "profiles": [
    {
      "id": "legacy-shared",
      "name": "现有共用账户",
      "enabled": true,
      "providers": [
        {
          "id": "apimart",
          "enabled": true,
          "primary": true,
          "billing_scope": "department",
          "base_url": "https://example.invalid/v1",
          "protocol": "openai",
          "image_models": [],
          "chat_models": [],
          "video_models": []
        }
      ]
    }
  ]
}
```

### 5.3 凭据

凭据必须由 `(api_profile_id, provider_id, credential_kind)` 唯一定位。

短期可延续服务端环境配置方式，但变量名需要包含稳定配置组 ID。正式命名规则须在实施前确定，并覆盖：

- 普通 API Key；
- RunningHub 普通 Key；
- RunningHub 钱包 Key；
- 火山引擎 API Key；
- 火山引擎 Access Key ID；
- 火山引擎 Secret Access Key；
- ModelScope Token；
- 其他平台的特殊凭据。

安全要求：

- 真实凭据不得出现在 Git 提交中；
- `API/.env` 当前仍被跟踪，正式实施前必须制定安全迁移方案；
- 建议保留不含真实值的示例配置；
- 配置文件、备份文件和日志应设置适当访问权限；
- 后续可评估 Windows 凭据存储或其他密钥管理方式，但不作为首阶段阻塞项。

## 6. 服务端解析模型

### 6.1 请求解析

普通请求的权威链路：

```text
认证用户
  → 读取用户的 api_profile_id
  → 校验配置组已启用
  → 在该配置组内解析 provider_id
  → 读取该组的平台连接
  → 读取该组的凭据
  → 调用上游
```

普通用户请求可以包含 `provider_id` 和 `model`，但不允许决定 `api_profile_id`。

### 6.2 统一解析层

后续实现应形成单一入口，概念职责如下：

```text
resolve_api_profile_for_user(user)
resolve_provider_for_user(user, provider_id, allow_default)
resolve_provider_credentials(api_profile_id, provider)
```

上游 helper 应接收已经解析好的运行时 provider，或显式接收不可变的配置组上下文。不得在深层 helper 中重新从全局配置猜测当前用户。

### 6.3 平台回退

- 请求未指定平台：使用当前配置组的默认平台；
- 请求明确指定本组平台：使用该平台；
- 请求明确指定不存在或未启用的平台：返回用户可读错误；
- 不得回退到其他配置组；
- 不得因为旧的本地存储残留而静默换用其他付费账户。

### 6.4 普通用户与管理员返回差异

普通用户只需要看到：

- 当前组允许的平台；
- 平台显示名称；
- 模型清单；
- 能力与启用状态；
- 必要的非敏感参数定义。

普通用户不应看到：

- 其他配置组；
- 密钥预览；
- 环境变量名；
- 凭据类型细节；
- 管理员备注或内部账户信息。

管理员可在明确选定配置组后管理其平台和凭据，但响应仍不得返回真实密钥。

## 7. 异步任务与后台执行

异步任务至少保存：

```json
{
  "id": "task-id",
  "user_id": "user-id",
  "api_profile_id": "ui-budget",
  "provider_id": "apimart",
  "model": "model-name",
  "usage_event_id": "usage-id",
  "status": "queued"
}
```

规则：

- 提交时完成身份、配额、配置组和平台校验；
- 后台 worker 使用任务中固定的配置组；
- 轮询接口按任务所有者鉴权；
- 客户端不能在轮询时换组；
- 用户后来被调组，不改变旧任务归属；
- 配置组停用或密钥轮换时，需要明确既有任务的处理策略；
- 如上游任务查询依赖原账户，应保留足够的非敏感关联信息；
- 不在任务记录中保存真实密钥。

## 8. 注册、分配与权限

### 8.1 新用户

推荐流程：

1. 用户注册并填写组织信息；
2. 账号进入“待管理员分配 API 配置组”状态；
3. 管理员核实部门并绑定配置组；
4. 用户获得对应的生成权限。

用户自填部门不能直接获得某部门经费账户。

### 8.2 管理员

管理员可以：

- 创建、复制、重命名、停用配置组；
- 管理配置组内的平台连接；
- 分配或调整用户配置组；
- 查看配置组用量、告警和健康状态；
- 测试当前明确选中的配置组连接。

建议复制配置组时默认不复制凭据，只复制平台、模型和非敏感配置。

## 9. 审计、配额与对账

用量事件建议新增：

- `api_profile_id`；
- `api_profile_name` 快照；
- `billing_scope`；
- `provider_id`；
- `provider_name` 快照；
- `model`；
- 上游任务 ID；
- 上游 usage/token；
- 非敏感配置版本；
- 原有用户、部门、功能、耗时和状态字段。

配置组层面应支持：

- 图片、视频、LLM 调用统计；
- 平台与模型构成；
- 成功率和失败率；
- 并发限制；
- 软性预算告警；
- 必要时的硬配额；
- 与上游账单差异核对。

系统审计用于内部归属和异常排查，财务结算仍以上游独立账户账单为最终依据。

## 10. 分阶段迁移计划

### M0：基线与备份

- 记录当前 Git 状态和已有用户修改；
- 备份用户、平台、会话、审计和相关配置；
- 记录主要入口的当前行为；
- 建立路由清单和验证基线；
- 不启动不必要的服务，避免运行时迁移噪声。

退出条件：可以明确区分改造前问题和改造引入的问题。

### M1：兼容数据模型

- 增加 API 配置组结构和版本；
- 创建“现有共用账户”兼容组；
- 给现有用户分配兼容组；
- 保持现有调用行为不变；
- 增加旧格式读取兼容和可重复迁移。

退出条件：旧用户、旧平台和旧页面行为不变，重载后数据不丢失。

### M2：管理员配置能力

- 增加配置组管理；
- 增加用户配置组分配；
- 增加 API 设置页配置组切换；
- 普通用户只读取自己的有效平台能力；
- 新用户进入待分配状态。

退出条件：管理边界正确，但生成链路仍可处于兼容模式。

### M3：服务端作用域解析层

- 实现统一配置组、平台和凭据解析；
- 禁止客户端选择配置组；
- 去除明确平台不存在时的全局回退；
- 使用假上游验证多用户并发不串凭据。

退出条件：核心隔离测试全部通过。

### M4：逐平台迁移调用链

建议顺序：

1. 普通 OpenAI 兼容图片；
2. LLM；
3. 视频；
4. RunningHub；
5. 火山引擎；
6. ModelScope；
7. 即梦、Codex、Gemini、本地 ComfyUI和其他入口。

每个平台族单独修改、验证和提交。

退出条件：入口清单中所有付费调用均已通过统一解析层。

### M5：异步任务与扩展

- 固定异步任务配置组；
- 验证刷新恢复和任务轮询；
- 验证 Chrome、Photoshop Bearer 身份；
- 验证任务所有者和管理员权限。

退出条件：异步和扩展入口无跨组风险。

### M6：审计、配额与管理视图

- 增加配置组用量字段；
- 增加配置组维度汇总；
- 增加共享费用标记；
- 增加预算告警和并发策略；
- 验证内部统计与假上游记录一致。

退出条件：可以稳定按配置组追踪和导出用量。

### M7：灰度切换与旧账户退役

1. 所有用户先保留在兼容组；
2. 配置四个部门组；
3. 先迁移低风险部门；
4. 观察调用、失败率和上游账单；
5. 逐部门迁移；
6. 停用并轮换旧共用凭据；
7. 在稳定运行一个发布周期后清理兼容逻辑。

退出条件：所有部门独立计费，旧共用账户不再产生新费用。

## 11. 兼容、灰度与回滚

- 初始所有用户绑定 `legacy-shared`，避免改造上线即中断；
- 新解析层在完成隔离验证前不直接切换所有入口；
- 数据迁移带版本号并可重复执行；
- 每阶段保留明确的 Git 回滚点；
- 每次迁移前备份运行时 JSON 和部署凭据；
- 不删除旧字段，直到新旧格式至少稳定运行一个发布周期；
- 配置组停用优先阻止新任务，不粗暴破坏已提交任务；
- 回滚不得恢复已经暴露或已决定轮换的旧密钥；
- 真实切换按部门灰度，不做一次性全量迁移。

## 12. 主要风险

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 按请求修改全局密钥 | 并发串账 | 使用不可变请求/任务作用域 |
| 信任客户端配置组 | 越权使用 | 仅从认证用户记录解析 |
| 平台不存在时全局回退 | 错误计费 | 明确指定失败即报错 |
| 异步任务未保存配置组 | 刷新或调组后串账 | 提交时固定配置组 |
| 自填部门直接授权 | 部门冒用 | 管理员分配配置组 |
| 特殊凭据遗漏 | 部分平台仍共用 | 使用入口清单逐项关闭 |
| 普通用户看到配置细节 | 信息泄漏 | 区分管理员和用户响应 |
| 密钥进入 Git 或日志 | 凭据泄漏 | 部署专用存储、掩码与检查 |
| 一次性大改 | 难定位、难回滚 | 分阶段、逐平台迁移 |
| 真实平台测试成本高 | 额外费用 | 假上游为主，单次低成本冒烟 |

## 13. 完成标准

只有同时满足以下条件，才视为最终改造完成：

- 一个服务端、一个访问地址；
- 每个正式用户都有管理员确认的 `api_profile_id`；
- 每个部门使用独立充值账户或被明确标记的共享资源；
- 用户无法读取或调用其他配置组；
- 所有平台和生成入口通过统一解析层；
- 异步任务与扩展入口通过隔离验证；
- 无跨组自动回退；
- 密钥不出现在响应、日志、审计和 Git 中；
- 用量可按配置组统计并与上游账单核对；
- 旧用户和旧数据迁移完成；
- 旧共用账户已停用或明确保留用途；
- 路由清单全部关闭；
- 阶段验收和隔离测试全部通过；
- 已记录外部平台中未能自动验证的项目。

## 14. 后续协作规则

每次开发任务应明确：

- 本次只处理哪个里程碑；
- 依据本文件的哪些章节；
- 对应入口清单中的哪些行；
- 明确不处理什么；
- 修改文件；
- 自动测试与手工验证；
- 新发现风险与设计决定；
- 是否满足本阶段退出条件。

如果实现与本文件冲突，应先更新并确认设计决定，再修改业务代码。
