# 管理台用量时间范围改版设计

## 目标

管理台「请求趋势」右上角的时间范围只能选到 1 天，无法回答「最近 10 天到半年用量涨得多快」。本设计把它改成**页面级统一时间范围**：最短 1 小时、最长半年（180 天，与审计保留期一致），并让趋势图、模型用量谱、服务健康度、部门对比、用量明细与导出共用同一区间。同时修掉长区间必然踩到的两个缺陷：按天聚合对齐错误与每次请求重复解析整个审计库。

## 现状与问题

- `static/admin.html` 内联脚本里 `rangeOptions` 只有 `15分钟 / 1小时 / 6小时 / 1天`，`updateRange()` 以「现在」为锚点向前回推。
- 这 4 档驱动趋势图、模型用量谱、服务健康度、部门对比；但**「用量明细」表格不读 `rangeState`**，只受图表下钻的 `chartState` 控制。结果是切档后图是 1 天、表是全量，两处口径不一致。
- 后端 `filter_usage_events_for_request()` 用 `created_at_iso` 字符串比较，本身不限范围；审计保留 `retention_days` 默认 180 天，半年数据本来就在，只是前端选不到。
- `main.py` 的 `admin_usage_analytics` 里 bucket 对齐只对「分钟」取模、不归零小时：`bucket_minutes=1440` 会为同一天的不同小时各出一个点（半年区间画出数千点而不是约 180 点），`360` 同样错位。
- `usage_events()` 每次请求重读并解析全部审计 JSONL、无缓存。实测近 3 个月：43,574 行 / **13,316 条唯一事件**（同一事件在提交、轮询、收口时重复写 3~4 行）/ 解析去重 **0.289s**；管理台一次加载要打 4~5 个用量接口，等于每次加载白烧约 1.5s、半年约 3s。

## 范围

包含：`static/admin.html`（范围条 UI 与内联脚本）、`static/js/admin-dashboard-v2.js`（范围条装配与刷新联动）、`static/css/admin-dashboard-v2.css`（样式）、`main.py` 用量接口段的 bucket 对齐与审计缓存、对应测试。

不包含：费用金额口径（现有审计只有次数、状态、耗时、配置组与计费性质，没有金额）、按天/按小时预聚合的物化索引、导出流式改造、管理台 i18n 装载。

授权边界不变：区间只是既有 `/api/admin/usage*` 接口上的查询参数，全部仍由 `require_admin` 保护；本设计不新增接口，也不放宽任何端点。

`admin.html` 整页是中文硬编码、**没有加载 `i18n.js`**（只有 `theme.js`、`lucide.js`、`admin-dashboard-v2.js`），新增文案按该页面既有约定不加 i18n 词条；加了也没有装载方，属于死代码。这偏离仓库「新增用户文本必须补齐中英文词条」的约束，需在交付说明中注明。

## 范围模型

页面级单例 `timeScope = {mode, key, start_at, end_at, bucket_minutes, compare}`，所有面板只读它，不再各自持有时间状态。

预设为滚动窗口（锚定「现在」，刷新时推进）：

| 预设 | 跨度 | 自动粒度 | 半年档点数 |
| --- | --- | --- | --- |
| 1小时 | 60 分钟 | 1 分钟 | 60 |
| 6小时 | 360 分钟 | 5 分钟 | 72 |
| 24小时 | 1440 分钟 | 15 分钟 | 96 |
| 7天 | 10080 分钟 | 1 小时 | 168 |
| 30天 | 43200 分钟 | 6 小时 | 120 |
| 90天 | 129600 分钟 | 1 天 | 90 |
| 半年 | 180 天 | 1 天 | ≤181 |

自定义区间为显式 `[start, end]`，分钟精度，选定后固定不漂移，便于复现与对照。

校验规则：

- 跨度下限 1 小时；上限为 `min(180 天, usage_policy.retention_days)`。保留期已由 `GET /api/admin/usage-policy` 返回，`load()` 早就在拉这个接口，**不需要新增后端接口**。
- `end` 不晚于当前时间，`start < end`；越界时就地提示并禁用「应用」，不发请求。

区间语义沿用现状：`start_at` 含、`end_at` 含，前端照旧发送 `end_at = 选定结束 + 1 分钟`，**不改动后端字符串比较契约**。

粒度按跨度自动映射，并可在下拉里手动覆盖（1分/5分/15分/1时/6时/1天）；手动粒度只改变展示聚合，不改变筛选区间。

「对比上一周期」取等长的紧邻前一窗口 `[start-len, start)`：图上叠一条虚线，指标卡显示涨跌百分比。实现为用平移后的区间再请求一次 analytics——审计解析已被缓存，额外成本只是一次聚合。

选择（模式、预设、对比开关、手动粒度）记入 localStorage，仅作展示偏好，不作为权限或数据来源。

## UI

- **位置变更**：范围条从「请求趋势」右上角移到 **workspace 导航下方常驻**，概览与「调用排障」都可见。因为「用量明细」在「调用排障」分区，若范围条只留在概览，在表格页换范围必须来回切分区。
- **三段式布局**：左＝预设按钮组（7 档）+「自定义 2026-08-12 ～ 09-10」按钮（展开 popover）；中＝聚合粒度下拉；右＝「对比上一周期」开关与刷新。
- **第二行是区间回显**（当前区间 · 共 N 天 / N 小时 / N 分钟（按跨度自动选单位）· 每点=N · 对比区间 · 可查最早日期）。它是「单一事实来源」的可视化，各面板不再显示各自不同的时间。
- **自定义 popover**：开始/结束 `datetime-local` + 快捷项（最近1小时 / 最近24小时 / 今天 / 昨天 / 本周 / 本月 / 上月）+ 实时跨度提示 + 上下限校验 + 取消/应用。
- **趋势图头部**：标题下方一行 caption（`2026-03-15 ～ 2026-09-10 · 按天聚合`），图例增加「上一周期」虚线项，原提示语改为「点选＝缩放到该点，拖拽＝框选子区间」。
- **时间轴标签随跨度切换**：≤24 小时用 `HH:MM`；≤7 天用 `MM-DD HH:MM`；更长用 `MM-DD`，跨年补 `YYYY-MM-DD`。
- **下钻语义修正**：点选/拖拽＝把**整个页面**的范围缩放到该子区间，图表、表格、部门对比一起变；时间 chip 的 `×` 回到上一级（保留一层返回栈）。不再出现「图上 1 天、表里全量」的错位。
- **下钻下限**：最小窗口＝当前粒度（按天视图最小 1 天，1 小时视图按分钟时最小 1 分钟）。`1 小时`下限只约束范围选择器；否则在 1 小时视图上点一个点会被强制撑成 1 小时，等于无法下钻。
- **用量明细头部**回显「按当前区间过滤：… 共 N 条 · 第 X / Y 页」。
- **响应式**：≤760px 时范围条纵向堆叠，预设组横向滚动。

## 服务端修正

1. **bucket 对齐**（`admin_usage_analytics`）：以「当日已过分钟数」取模再还原时刻——`minute_of_day = hour*60 + minute`，`aligned = minute_of_day - minute_of_day % min(bucket_minutes, 1440)`，桶时刻为 `replace(hour=aligned//60, minute=aligned%60, second=0, microsecond=0)`。效果：`1440` 归到 `00:00`（一天一点）、`360` 归到 `00/06/12/18`、`15/30/60` 行为不变。前端 `floorTime()` 换成同一算法，供拖拽框选吸附使用（它现在也只在分钟上取模，粗粒度下会算错）。
2. **审计解析缓存**：`usage_events()` 增加模块级缓存，键为排序后的 `(路径, size, mtime_ns)` 元组加 `retention_days`；读写与 `append_usage_event` 共用既有 `USAGE_AUDIT_LOCK`，命中时返回浅拷贝以免调用方改到缓存。任一审计文件出现或 size/mtime 变化即整体重解析，不做增量尾解析——每个事件的追加次数只有 3~4 次，全量缓存命中率已经足够。
3. **不改 `asyncio.to_thread`**：实测聚合部分 0.065s（半年约 0.13s），缓存后瓶颈不在聚合，不值得把 160 行的 handler 拆成线程函数。
4. **导出保持一次性序列化**：实测导出体 3 个月 9.5MB（compact）/ 10.2MB（`indent=2`），半年约 19 / 20MB，当前量级内存可接受；改为前端在条数超过 20000 时先确认（用当前区间已有的 `total` 与估算体积）。流式导出留到数据再涨 5~10 倍时做。

## 失败行为

- 自定义跨度非法（<1 小时、早于保留起点、`end ≤ start`、`end` 晚于当前时间）：就地提示、禁用「应用」，不发请求。
- 区间内没有记录：保留现有「当前时间范围内没有用量记录」占位，不报错。
- `retention_days` 变小：范围条上限与「可查最早日期」随之更新；已选区间超界时裁剪到上限并提示。
- 缓存：不返回过期结果——键变化即重解析；缓存缺失只影响首次延迟，不影响正确性。
- 对比区间落在保留期之外（例如半年档对比上一个半年）：按空数据渲染，指标卡不显示涨跌百分比，并提示「对比区间无数据」，不报错。
- 导出条数为 0：不触发确认提示，直接导出空集合（保持现有行为）。

## 验收

后端（新增 `tests/test_admin_usage_time_range.py`，沿用 `tests/test_admin_dashboard.py` 的 `patch require_admin` + 假 request 模式，配临时 `USAGE_AUDIT_DIR`）：

- bucket 对齐回归：`15/60/360/1440` 四档分别断言；`1440` 同一天只出一个 `00:00` 桶，`360` 只落在 `00/06/12/18`。
- 区间含端语义：`end_at = 选定结束 + 1 分钟` 含最后一分钟；1 小时窗口只返回该窗口内的事件。
- 半年窗口：合成 200 天数据后桶数 ≤181，且 `summary.total` 与筛选出的条数一致。
- 缓存：连续两次 analytics 只解析一次（计数断言）；`append_usage_event` 后新事件立即可见；改 `retention_days` 后结果随路径集变化。
- 导出：`filters` 回显 `start_at/end_at`，body 可 JSON 解析且条数与筛选一致。

保持绿：`test_admin_dashboard.py`、`test_m6_usage_accounting.py`、`test_departments.py`、`test_api_profiles.py`。

静态检查：`ast.parse main.py`、抽出的内联脚本 `node --check`、`node --check static/js/admin-dashboard-v2.js`、`node static/js/i18n/validate-i18n.js`、`git diff --check`。

浏览器实测（需管理员会话）：半年档趋势图为按天点且轴标签为 `MM-DD`；切档后趋势图、模型用量谱、健康度、部门对比、用量明细与导出同一区间；1 小时档轴标签为 `HH:MM`；自定义跨度 <1 小时或早于保留起点时无法应用；下钻把整页缩放到子区间且 chip 可返回；对比虚线为等长紧邻前窗；用量明细条数随区间变化。
