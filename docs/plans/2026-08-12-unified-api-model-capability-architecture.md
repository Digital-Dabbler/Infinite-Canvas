# 多 API 平台统一模型能力架构改造计划

日期：2026-08-12
状态：实施中（核心改造完成，待浏览器联调验收）
范围：智能画布图片/视频生成 Composer、模型能力发现、生成请求序列化、平台适配与画布兼容

## 实施记录（2026-08-12）

已完成：

- 修复视频模型切换时调用不存在 helper 的既有错误。
- 后端为全部 API 平台返回统一的图片/视频能力对象；RunningHub 使用上游 schema，APIMART、ModelScope 使用受控适配器，其余平台使用安全通用回退。
- Composer 的 API、火山引擎和 ModelScope 图片/视频面板改为按能力对象渲染；图片、视频的比例、分辨率、时长、输入限制和已支持开关不再使用平台专属旧布局。
- 图片请求层改为统一读取能力缓存提交比例、尺寸与显式宽高；视频请求继续使用现有平台适配器提交已声明的字段。
- 平台保存会保留已声明的 `model_capabilities`，并由服务端白名单过滤，避免将未适配参数渲染成可提交控件。

待验收：

- 使用已登录的本地服务进行浏览器切换平台、加载模型、参考图比例、图片/视频异步任务的交互回归。
- 对每个平台在不产生不必要费用的前提下执行状态级或单次低成本请求验证，并补充结果到第 10 节验收矩阵。

## 1. 背景与问题

Infinite Canvas 已接入 RunningHub、APIMART、ModelScope、火山引擎、OpenAI 兼容平台、CLI 和 ComfyUI 等多种生成来源。当前智能画布的生成面板存在两套不一致的实现：

- RunningHub 模型会拉取上游参数定义，并按模型动态展示输入要求、比例、分辨率、尺寸、质量与扩展参数。
- APIMART、普通 OpenAI 兼容平台等使用固定的通用面板，只显示预设尺寸、固定质量和张数。
- RunningHub 的扩展参数会被校验并提交；非 RunningHub 平台目前不会获得同等的能力描述，`model_params` 也不会被实际转译到各自上游请求。
- 视频生成同样分裂：RunningHub 依据模型 schema 约束参考图、首尾帧、比例、时长和开关；其他平台仍使用固定参数集合，可能隐藏支持项或显示不支持项。

因此，平台切换会改变的不只是视觉布局，而是实际可配置、可提交和可验证的能力范围。

## 2. 总体目标

将所有 API 平台的图片与视频生成统一为 **模型能力驱动** 的系统，前端交互和后端处理方式向现有 RunningHub 的动态能力机制看齐：

1. 用户选择平台和模型后，面板自动显示该模型真实支持的参数。
2. 每个可见参数都必须能被校验、保存、恢复并映射到对应平台的上游请求。
3. 新增 API 平台只需补充能力来源与请求适配，不再复制一套生成面板。
4. 无法获得模型 schema 的平台安全降级到已知通用能力；不得猜测、伪造或发送未声明的参数。
5. 保持旧画布、既有平台配置和生成接口消费者的兼容性。

## 3. “能力一致”的定义

本改造中的“一致”指统一的能力模型、交互模式、保存方式和提交保障，不代表所有上游平台显示相同按钮。

例如：

- 某 APIMART 图片模型支持比例、分辨率、参考图与官方回退时，应显示这些项目，并按 APIMART 协议提交。
- 某模型只支持文生图，则不显示图片输入，也不能引用图片后继续提交。
- 某视频模型要求首帧或支持首尾帧时，面板应明确表达该约束；纯文本视频模型不应显示无效的图片输入。
- 模型未提供可发现的 schema 时，仅展示该平台适配器已确认的通用字段，并提示能力信息来源，而非展示一组可能无效的“万能参数”。

## 4. 统一能力协议

### 4.1 规范化模型能力对象

后端对所有平台返回统一的模型能力对象；前端不直接依赖 RunningHub 的原始字段。建议的稳定字段包括：

```json
{
  "provider": "apimart",
  "model": "gemini-3.1-flash-image-preview",
  "kind": "image",
  "discovered": true,
  "source": "provider-schema | adapter | configured | fallback",
  "fields": [
    {
      "key": "aspectRatio",
      "type": "ENUM",
      "required": false,
      "label": "比例",
      "default": "1:1",
      "options": [{"value": "1:1", "label": "1:1"}]
    }
  ],
  "input": {
    "images": {"accepted": true, "required": false, "max": 6},
    "videos": {"accepted": false, "required": false, "max": 0},
    "audios": {"accepted": false, "required": false, "max": 0},
    "firstFrame": false,
    "lastFrame": false
  }
}
```

`fields` 用于渲染控件和服务端校验；`input` 用于模型筛选、输入轨道提示和提交前检查。内部可保留平台原始字段，但不得直接暴露密钥、私有 URL 或未经清洗的上游内容。

### 4.2 统一字段类型

至少支持以下类型，并允许后续在不破坏旧字段的前提下扩展：

- 媒体输入：`IMAGE`、`VIDEO`、`AUDIO`、首帧、尾帧、蒙版。
- 尺寸：比例、原图/自适应比例、分辨率、尺寸档位、显式宽高。
- 生成参数：数量、质量、时长、随机种子、提示词增强、放大、音频、水印、固定镜头。
- 通用控件：枚举、布尔、整数、浮点、文本、多行文本。
- 平台扩展参数：必须有明确 `key`、类型、范围、默认值与序列化规则。

### 4.3 能力来源优先级

同一模型的能力按以下顺序合并，后者仅补足缺失项，不可绕过安全限制：

1. 上游公开的、当前账号可访问的模型 schema 或能力接口。
2. 平台适配器中经过验证的模型能力规则。
3. 管理端/API 配置中保存的显式能力补充数据。
4. 可证明的通用协议能力（例如 OpenAI Images 的 `model`、`prompt`、`size`）。
5. 安全降级：仅保留已知字段，并标记 `discovered: false`。

RunningHub 继续使用远端模型注册表和参数定义；其原始 schema 需先归一化后再交给前端。其他平台不得因为没有远端 schema 而返回虚假的“全部支持”。

## 5. 目标架构

### 5.1 后端：平台能力适配层

为每个生成平台建立清晰的适配职责，而不是将 `provider_id` 条件继续散布在路由和前端中：

| 适配职责 | 说明 |
| --- | --- |
| `list_models` | 返回已配置且可用的图片、视频、文本模型。 |
| `get_capabilities` | 获取并归一化单模型或批量模型能力，可带短期缓存。 |
| `validate_request` | 按能力对象验证媒体输入、必填字段、选项、范围与依赖关系。 |
| `serialize_request` | 将统一请求转换为该平台实际要求的字段、JSON 或 multipart 结构。 |
| `parse_response` | 沿用现有媒体结果提取，确保本地 URL 与异步任务恢复契约不变。 |

保留 `/api/image-model-capabilities` 和 `/api/video-model-capabilities` 的路径兼容性，但将其响应扩展为全平台统一能力结果。新代码不得只因 `is_runninghub_provider()` 才查询、缓存或渲染能力。

### 5.2 前端：单一动态 Composer

智能画布 Composer 只消费统一能力对象：

1. 选择平台后加载对应媒体类型的模型列表。
2. 选择模型后读取缓存能力，并在后台刷新。
3. 按能力渲染输入提示、尺寸控件、参数控件和错误状态。
4. 模型或输入变化时，自动筛除与当前输入不兼容的模型，保留用户在兼容模型上的最近选择。
5. 保存的 `runSettings` 中保存规范化字段与平台扩展参数；切换平台不得串用不兼容字段。

RunningHub、APIMART、ModelScope、火山引擎、普通 API、CLI 与 ComfyUI 可以有不同的能力提供者，但不能再各自维护平行的图片/视频面板 HTML 结构。

### 5.3 统一请求对象

前端将生成设置构造成平台无关的请求对象，例如：

```json
{
  "provider_id": "...",
  "model": "...",
  "kind": "image | video",
  "prompt": "...",
  "input_media": [],
  "size": {"mode": "preset", "ratio": "16:9", "resolution": "2k"},
  "parameters": {"quality": "high", "seed": 1234}
}
```

后端先根据能力对象验证该请求，再交给适配器转换。不得将任意 `parameters` 原样透传给上游：仅允许 schema 声明的字段和值通过。

## 6. 图片生成改造

### 6.1 面板行为

- 统一显示模型选择、模型输入要求和参数来源状态。
- 比例支持固定比例、原图比例、自适应比例与自定义比例；只展示模型实际允许的选项。
- 尺寸支持档位、分辨率或宽高输入；当模型要求其中一种时，隐藏其他冲突控件。
- 自动尺寸仅在模型或适配器明确支持时显示；不能仅依赖模型名称猜测。
- 质量、数量、种子、负面提示词和其他扩展参数均按 schema 展示、校验与保存。
- 参考图的可选/必填、数量上限和角色（图像、蒙版等）必须在生成前校验。

### 6.2 APIMART 专项要求

- 将现有尺寸转换逻辑纳入 APIMART 图片适配器，而非散落在通用请求路径。
- 根据实际模型能力展示允许的比例和分辨率；例如被上游限制为 1K 的模型，面板应禁用或说明 2K/4K，而不是允许选择后静默降级。
- 保持现有 `image_urls` 图生图、官方回退和错误信息语义。
- 未确认上游支持前，不新增或透传 APIMART 专有参数。

### 6.3 通用 OpenAI 兼容平台

- 以公开协议和配置的请求模式为能力下限。
- 对 Responses、Images、编辑、代理视频等既有请求模式建立明确的能力映射。
- 对模型名称规则仅作为最后兼容回退；逐步允许管理员配置模型能力元数据，避免永久依赖字符串猜测。

## 7. 视频生成改造

### 7.1 统一视频能力

视频能力对象至少表达：

- 文生视频、图生视频、首帧、尾帧和多模态输入；
- 图片、视频、音频的可选/必填与数量上限；
- 比例或自适应比例；
- 分辨率、时长、批量数量；
- 音频、提示词增强、固定镜头、水印、超分和其他平台专有开关。

### 7.2 模型筛选与输入轨道

- 有参考图时，只提供接受图片的模型；无参考图时，排除要求图片的模型。
- 首尾帧模型必须明确角色和必填关系，不能只将所有图片混入普通参考图列表。
- 模型能力未返回时可使用保守的名称规则做临时筛选，但必须保留“未知”模型，并在能力返回后重新校正。
- 修复当前视频模型记忆逻辑中的未定义 helper 调用，确保切换模型不会在运行时报错。

### 7.3 视频请求适配

每个平台将统一的视频参数映射到自身的请求字段。平台不支持的参数不得发送；必要时在提交前返回可读错误，而不是让上游以模糊错误失败。

## 8. 数据、兼容与安全

### 8.1 画布兼容

- 保留现有 `runSettings`、`provider_id`、`model`、`videoProvider`、`videoModel` 等字段。
- 加入版本化的能力设置字段和参数容器，旧画布加载时提供默认值。
- 保存时移除仅用于能力请求、临时缓存和任务恢复的瞬态字段。
- 旧画布在未重新选择模型时仍可生成；发现已失效参数时应提示用户并提供安全回退。

### 8.2 配置兼容

- 继续支持既有 `api_providers.json` 结构和管理员设置页面。
- 如需新增静态能力补充，使用可选、版本化、可校验的配置字段；不将密钥或上游凭据写入其中。
- 服务端能力缓存按 API Profile 与 provider/model 隔离，避免跨账号泄露可用模型或私有配置。

### 8.3 参数安全

- 所有字段在服务端基于能力 schema 白名单校验、类型转换、范围限制和长度限制。
- `model_params` 迁移为受控的规范化参数容器，不能成为任意 JSON 透传通道。
- 媒体路径、远程 URL、文件数量和文件大小继续复用现有安全校验与上限。
- 错误响应保留用户可读原因，但不泄露 API Key、Cookie、Token、上游内部堆栈或绝对本机路径。

## 9. 分阶段实施计划

### 阶段 0：稳定当前分支

1. 修复视频模型切换中调用未定义 helper 的问题。
2. 梳理现有未提交改动，确保不覆盖用户正在进行的提示词节点工作。
3. 为当前 RunningHub、APIMART 图片/视频面板记录浏览器基线截图与请求体证据。

验收：模型切换无控制台错误；现有生成设置可保存、刷新和恢复。

### 阶段 1：建立服务端统一能力契约

1. 抽取能力归一化、缓存、白名单验证和平台适配入口。
2. 扩展图片/视频能力接口，使所有 provider 返回统一结构。
3. 保持旧接口路径、错误格式和认证边界兼容。
4. 为无 schema 平台实现明确的 fallback 能力对象。

验收：每个已启用平台的图片/视频模型均能返回合法能力对象；不调用付费生成。

### 阶段 2：统一前端能力加载与渲染基础

1. 移除前端仅对 RunningHub 查询能力的条件。
2. 将图片、视频的能力缓存、加载状态、失败状态和模型选择逻辑改为 provider 无关。
3. 抽取共享的动态字段渲染器，保留现有视觉语言和中英文词条。
4. 将平台专用 DOM 分支收敛为能力适配，不复制 Composer 布局。

验收：切换任意平台不会出现旧布局闪回、丢失模型选择或控制台错误；无能力 schema 时显示受控降级状态。

### 阶段 3：图片请求与平台适配

1. 将统一图片设置转换为规范化请求对象。
2. 实现 RunningHub、APIMART、ModelScope、火山引擎、普通 API、CLI、ComfyUI 的图片参数验证与序列化。
3. 迁移 `model_params` 的使用方式，保证 UI 可见参数均被真实处理。
4. 特别验证 APIMART 的比例/分辨率、图生图、模型限制和官方回退。

验收：浏览器中每个可见图片参数均可追踪到服务端适配器；每个平台只做一次低成本或状态级测试。

### 阶段 4：视频请求与平台适配

1. 迁移文/图生视频、首尾帧、多模态输入、比例、分辨率和时长。
2. 将视频开关改为 capability 驱动，不支持则不显示且不发送。
3. 保留异步任务提交、轮询、停止、刷新恢复和统一用量事件的既有契约。

验收：文本视频、图生视频、首尾帧视频（在有对应模型时）均能通过前置验证；异步任务状态不重复计费。

### 阶段 5：迁移、回归与文档收尾

1. 为旧画布进行加载、保存、刷新和再次打开的兼容测试。
2. 补齐 API 设置和智能画布的用户提示及必要中英文词条。
3. 清理废弃的 RunningHub 专属 UI 分支，仅保留其能力提供者实现。
4. 更新本计划状态、实际变更文件、已验证平台和已知限制。

验收：完成第 10 节全部检查，工作区不包含运行时数据、密钥、媒体或缓存戳噪声。

## 10. 验收矩阵

下列矩阵按当前已配置平台执行；未配置或需要付费的项目记录为“未执行及原因”，不能以假数据宣称通过。

| 平台 | 图片能力 | 视频能力 | 重点验收 |
| --- | --- | --- | --- |
| RunningHub | 远端 schema | 远端 schema | 回归动态参数、工作流/App 与模型路径。 |
| APIMART | 适配器/已知 schema | 适配器/已知 schema | 比例/分辨率限制、图生图、模型专有规则。 |
| ModelScope | 平台适配 | 平台适配（如已配置） | 模型模式、尺寸与参考图约束。 |
| 火山引擎 | 平台适配 | 平台适配 | 现有图片/视频分支迁入统一协议。 |
| OpenAI 兼容平台 | 通用或配置能力 | 通用或配置能力 | Images、Edits、Responses 等请求模式。 |
| CLI（即梦、GPT、Gemini） | CLI 适配 | CLI 适配（如支持） | 状态检查、参数映射和可读失败。 |
| ComfyUI | 工作流字段能力 | 工作流字段能力 | 保留工作流字段配置与本地实例行为。 |

每个适用单元至少验证：

1. 平台、媒体类型和模型切换。
2. 参数仅在模型支持时出现，必填参数有明确提示。
3. 参数变更后保存、刷新、重新选中节点仍正确恢复。
4. 前端请求与后端适配后的上游 payload 相符（日志不得包含密钥）。
5. 单次低成本生成或官方状态/连接测试；不默认进行批量或高质量付费调用。
6. 失败时保留既有节点结果和用户设置，并展示可恢复的错误。
7. 旧画布加载、保存、刷新和再次打开无数据丢失。

## 11. 代码与验证边界

预计涉及：

- `static/js/smart-canvas.js`
- `static/css/smart-canvas.css`（仅在统一控件需要样式收敛时）
- `static/js/i18n/smart-canvas.js`
- `main.py`
- 可能新增的、仅包含能力适配逻辑的后端模块或测试文件
- 本计划文件

不得无选择提交或覆盖：

- `API/.env`
- `data/*.json`、画布、会话、用量审计等运行时数据
- `assets/`、`output/`、`python/` 运行时产物
- 服务启动造成的静态 HTML 缓存戳变更

每个实施阶段至少执行与改动相称的检查：

```powershell
node --check static/js/smart-canvas.js
.\python\python.exe -c "import ast, pathlib; ast.parse(pathlib.Path('main.py').read_text(encoding='utf-8')); print('main.py syntax OK')"
git diff --check
git diff --stat
git status --short
```

同时必须进行对应的浏览器级交互验证；语法检查、模拟响应或仅查看源码均不能替代面板与实际请求链路验证。

## 12. 非范围与决策门槛

本计划不包含：

- 未经用户授权的批量、昂贵或高质量外部生成测试。
- 为无公开能力说明的上游 API 猜测私有参数。
- 改变账号、鉴权、用量审计、付费策略或 API Key 存储方式。
- 将所有平台强制伪装成完全相同的参数集合。

若某平台的公开文档、账号权限或实际接口与现有适配假设不一致，应在对应阶段停止该平台的参数扩展，记录证据并保留通用安全降级，而不是将未经确认的字段发布到生产面板。

## 13. 完成标准

本改造完成时，应同时满足：

1. 所有已启用 API 平台使用同一套能力驱动 Composer 设计。
2. 图片与视频模型均可按实际能力决定输入和参数，而非按平台名称选择旧/新布局。
3. UI 显示的每个参数均通过服务端白名单校验并被对应适配器处理。
4. 新增平台可通过增加模型能力提供者与请求适配器接入，无需重写生成面板。
5. RunningHub 的现有动态能力、异步任务和工作流/App 能力不回退。
6. 旧画布、已有平台配置、生成任务恢复和用量事件契约保持兼容。
7. 通过相关语法检查、`git diff --check`、目标浏览器交互测试与平台验收矩阵，并明确未执行项及原因。
